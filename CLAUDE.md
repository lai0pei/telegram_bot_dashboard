## Commands

```sh
npm run dev           # dev server on :3000
npm run build         # production build (output: "standalone")
npm run lint          # eslint .
npx tsc --noEmit      # type-check (no dedicated script)
npm run db:generate   # generate a Drizzle migration after editing lib/db/schema.ts

```

There is no test suite. Required env vars are in `.env.example` (`API_ID`, `API_HASH`, `APP_SECRET`, `POSTGRES_PASSWORD`, plus `DATABASE_URL` outside docker-compose; optional `REGISTRATION_ENABLED`, `ALLOWED_TELEGRAM_USER_IDS`, `HOST_BIND`, `TRUSTED_PROXY_HOPS`).

## What this is

A self-hosted dashboard, signed into by **scanning a QR code with Telegram** (no dashboard password), where each dashboard account can link multiple **Telegram user accounts over MTProto** (via `teleproto`, a GramJS-compatible client) to list/create/delete their bots and manage their channels/groups, and calls the plain **Bot API** with each bot's token for everything a token can do itself (name, descriptions, commands, webhook, messages). Bot creation/deletion/token fetch/revoke have no API a user session can use (Bot API: none; MTProto `bots.exportBotToken` is callable only by a *manager bot*, `bots.createBot` only makes *managed* bots, and there is no delete method), so `lib/botfather.ts` scripts a chat with @BotFather (clicking its inline buttons where possible). If BotFather's wording changes, those flows break; deletion double-checks against `bots.getAdminedBots` so a reworded success message doesn't report a failure.

## Architecture

**Two identities, one cookie** (`lib/auth.ts`): a dashboard account (`users` table — `username` is just a display name copied from Telegram at creation, not a credential) can link multiple Telegram accounts (`telegram_accounts` table, one row per linked account, `ownerUserId` → `users.id`). The single `tgdash_session` JWT cookie carries all three: `sub` (dashboard user ID), `ver` (that user's `sessionVersion`, bumped by "sign out other browsers" in Settings to invalidate other devices), and `activeTelegramAccountId` (which linked account bot/chat routes act as — re-signed whenever the user switches accounts, never a second cookie). `proxy.ts` redirects unauthenticated *page* requests to `/login` but lets all `/api/*` through — API routes enforce auth themselves (`lib/api-guard.ts`):
- `withSession` — routes that need the dashboard user but not a specific Telegram account (account management, `/api/me`, logout, the link-account wizard). Passes `userId` as the third handler arg.
- `withAuth` — every bot/chat route. Re-validates `activeTelegramAccountId` against the DB every request (catches an account unbound in another tab) and 409s with `code: "NO_ACTIVE_ACCOUNT"` if none is set; passes the Telegram account's `id` as the third handler arg `(req, ctx, telegramAccountId)`. Dynamic params are `await ctx.params`.
- `withAdmin` — everything under `app/api/admin/**` (the master-admin area: a read-only list of all dashboard users with usage counts, `lib/admin-users.ts`). Built on `withSession`; 403 `code: "NOT_ADMIN"` (never 401/409). Admin = any linked `telegram_accounts.telegramId` in `MASTER_ADMIN_TELEGRAM_IDS` (`lib/admin.ts`; **empty means nobody**, the opposite of `ALLOWED_TELEGRAM_USER_IDS`), looked up per request and never put in the JWT, so env changes apply at once; `revokedAt` is ignored so a session ended from the phone can't lock the admin out. These routes are deliberately cross-tenant and must never return tokens, messages, session strings or phone numbers. The sidebar's Admin link only reads `isAdmin` from `GET /api/telegram-accounts`; `app/(dashboard)/admin/page.tsx` leaves only on a real 403 `NOT_ADMIN`. `withSession`/`withAuth` also bump `users.lastActiveAt` via `touchLastActive` (`lib/users.ts`: fire-and-forget, at most one write per user per 5 min). **Admin actions** (`lib/admin-actions.ts`, `POST …/users/[id]/sign-out`, `…/suspend`, `DELETE …/users/[id]`): refused (422) on yourself or any master admin; each is written to `admin_actions` (append-only, `targetName` copied because the row outlives a deleted user) **in the same transaction** as the change. *Suspend* sets `users.suspendedAt` and bumps `sessionVersion` (open tabs get the existing 401 → sign-in page); `withSession`/`withAuth` also 401 on `suspendedAt` as a backstop; `finishLogin` returns `{ status: "suspended" }` (403 `ACCOUNT_SUSPENDED`) *before* touching the stored session. Background code skips a suspended user's bots **where it selects work** (`botNotSuspended`/`userNotSuspended`, `lib/suspension.ts`: poller, health check, scheduled messages, broadcasts, digest), never in `getBotForJob`: scheduled messages and broadcasts treat "bot not found" as a failure, so filtering there would fail queued work instead of pausing it. *Delete* needs the user to be suspended already plus their typed name, runs `unbindTelegramAccount` (`lib/unbind-account.ts`, also the user's own unbind) per account, then one transaction for the rest. **Access settings** (`app_settings` table, `lib/app-settings.ts`, `GET/PUT /api/admin/access`, Admin → Access tab): sign-ups open/closed and the linking allowlist. A stored row **overrides** the env var (`REGISTRATION_ENABLED`, `ALLOWED_TELEGRAM_USER_IDS`); `null` in the PUT deletes the row ("Reset to .env"), so an untouched deployment behaves exactly as before. The allowlist is `{ restrict, ids }` with an explicit switch (the env var's "empty means anyone" would let clearing the last ID silently open linking), and an unreadable stored allowlist **fails closed** (restricted to nobody; the admin still passes). Values are cached for 10 s and the cache is dropped on every write (single process). Changes are audited as `update_access` with the admin as the target. There are no foreign keys, so **any new table with a `bot_id` column must be added to `deleteBotRow`** (it had missed deep links, button templates, games, mini apps and daily stats).
- `withRateLimit` — wraps starting a sign-in QR (`POST /api/login/qr`) and the sign-in 2FA step (`/api/login/password`), per-IP since there's no dashboard user yet. Polling (`GET /api/login/qr`, every 2s) is intentionally unlimited.

**Sign-in is the same QR/2FA flow as linking, in two modes** (`lib/mtproto.ts`): `startQrLogin(mode, ownerUserId?)` / `pollQrLogin` / `submitLoginPassword` take `mode: "link" | "signin"`. `"link"` (used by `/api/auth/qr`+`/api/auth/password`, `withSession`) binds an extra account to the caller's existing `ownerUserId`. `"signin"` (used by the unauthenticated `/api/login/qr`+`/api/login/password`) has no caller yet — `finishLogin` resolves the dashboard user itself: an existing owner for that `telegramId` signs in as them; otherwise a new `users` row is created (`createUserForTelegram`, `lib/users.ts`), unless sign-ups are closed (`isRegistrationOpenFor`, `lib/app-settings.ts`: the Admin → Access value, else `REGISTRATION_ENABLED`) yields `{ status: "registration_closed" }`; the allowlist check is the async `isTelegramUserAllowed` from the same module, and both always let a master admin through. Either mode's `{ status: "logged_in" }` outcome now carries `userId`. Both route pairs share the HTTP mapping of outcomes → responses in `lib/login-response.ts` and the `QrLogin` component (`components/qr-login.tsx`, `apiBase` prop picks `/api/login` vs `/api/auth`). A sign-in or re-link also best-effort logs out that Telegram account's previous session (`endPreviousSession`) so Telegram's Devices list keeps one dashboard entry per account.

**Multi-tenant isolation is enforced by query scoping, not by the DB.** Every lookup in `lib/bots.ts` / `lib/chats.ts` takes `ownerUserId`, which is actually a `telegram_accounts.id` (bots/chats belong to a linked Telegram account, not directly to the dashboard user) — e.g. `getBotById(id, telegramAccountId)`. Any new data access must be scoped the same way. A Telegram account's `telegramId` is globally unique across `telegram_accounts` (enforced by a unique index) since the live MTProto client map is keyed by it — two dashboard users can never link the same Telegram account.

**Revoked Telegram sessions**: `getClient` wraps each client's `invoke` so any MTProto 401 (session terminated from the phone, etc.) sets `telegram_accounts.revokedAt` and throws `TelegramSessionRevokedError`, which `errorResponse`/`withAuth` turn into 409 `code: "SESSION_REVOKED"`. `GET /api/telegram-accounts` also probes live sessions (TTL-cached) and re-points the cookie off a revoked active account. Revoked rows keep their bots/chats; signing in or re-linking by QR clears `revokedAt`. On the client, `AccountsProvider` (`app/(dashboard)/accounts-context.tsx`) is the single account list — refreshes on focus/interval/`SESSION_REVOKED` and remounts the page when the active account changes.

**Bots added by token** (`bots.source = "token"`, `lib/token-bot.ts`, `addBotByToken`/`replaceBotToken` in `lib/bots.ts`, `POST /api/bots/token`, `PUT /api/bots/[id]/token`, `bots/add-token-dialog.tsx`): a bot the linked account does *not* own, added by pasting its token (verified with `getMe`; name/id come from Telegram). It runs on the Bot API like any bot (profile text, commands, rules, templates, builder, broadcasts, monitoring), but has no BotFather/MTProto relationship, so: the list sync (`pruneBotsNotIn`) never prunes it; `withLiveBotToken` never heals it and never clears its token (a 401 becomes `TokenBotTokenError` → 422, fixed with "Replace token", which must be the same bot id); `DELETE` only removes local rows ("Remove from dashboard", the token and any webhook stay); `lib/limits.ts` doesn't count it against the BotFather cap; and every owner-only route (`token` GET, `revoke`, `transfer`, `botfather-settings`, games/Mini Apps create/delete, `usernames`, `photo` writes) starts with `ownedBotOnly(bot)` → 422 (never 401/409). The UI hides the "Apps & games" section (`Section.ownerOnly`, `sectionGroupsFor`), the photo/usernames cards, and disables the BotFather switches. **One account per bot across all accounts**: the unique index `bots_telegram_id_unique` backs it, `BotHeldByAnotherAccountError` → 422, and the owner's own list sync skips such a bot and reports it in `skipped` instead of failing. A sync that really lists the bot turns the row `owned` (`upsertBotFromTelegram` sets `source`). Turning monitoring on asks for confirmation (the owner's own server may already read the bot's updates; a webhook blocks monitoring), and the add dialog warns when `getWebhookInfo` shows one. Unbinding a Telegram account deletes its token bots too, so the unbind prompt lists them (`tokenBots` in `/api/telegram-accounts`). A revoked account's token bots aren't reachable (`withAuth` 409s), so `attention.ts` keeps skipping them. The migration folder has stale SQLite files (`0015`–`0019`, snapshot `0006`) that `drizzle-kit generate` rejects; `0001_token_bots` was generated against a temp copy holding only the Postgres history.

**Secrets at rest**: MTProto session strings and bot tokens are AES-256-GCM encrypted with a key derived from `APP_SECRET` (`lib/crypto.ts`). Always go through `encrypt`/`decrypt`; use `maskSecret` when returning tokens in list views. There's no dashboard password to hash — Telegram's own auth (and 2FA, if the account has it) is the only credential check.

**Process-global state on `globalThis`** (survives dev hot-reload and module re-evaluation): the Postgres pool / Drizzle handle (`lib/db/index.ts`), per-account MTProto clients keyed by Telegram ID and in-progress login states (`lib/mtproto.ts`), and in-flight promise map (`lib/single-flight.ts`). Follow the `globalThis.__tgDash*` pattern for any new process-wide state. The app assumes a single Node process.

**Concurrency guards around BotFather / MTProto**:
- `lib/botfather.ts` holds a per-user lock so two flows never interleave in the same BotFather chat.
- `singleFlight(key, fn)` collapses duplicate concurrent calls (repeat clicks, parallel requests) into one promise — used for token healing, chat sync, invite regeneration, deletes.

**Token self-healing**: wrap Bot API calls in `withLiveBotToken(bot, userId, fn)` (`lib/bots.ts`). On a 401 it re-fetches the token from BotFather, saves it, and retries once (single-flighted, with a cooldown so a still-dead token doesn't reopen BotFather on every request).

**Background poller**: `instrumentation.ts` starts `lib/poller.ts` once per Node process; it long-polls `getUpdates` for every bot with `monitorEnabled` and advances `lastUpdateId`. It handles `message` (→ `bot_messages`, plus `bot_users` for *private* chats only), `edited_message` (updates the stored row in place), `callback_query` (stored as an "in" row; `answerCallbackQuery` only clears the spinner) and `my_chat_member` / group messages (→ `bot_chats`), plus `inline_query` / `chosen_inline_result` and the four `business_*` updates (see below). Each update is handled in its own try/catch: a non-database error skips that update, a database error (`isDatabaseError`, `lib/db/errors.ts`: a Postgres error or a lost connection) leaves the offset untouched so nothing is dropped (e.g. an unapplied migration or Postgres restarting). A webhook and monitoring are mutually exclusive for a bot. The poller also (a) applies **auto-replies** (`lib/auto-replies.ts`: `command` / `exact` / `contains` rules for messages, `callback` rules that answer a pressed button) — the reply is sent *last*, after every database write, so a retry of the update after a database error can't reply twice, and bot senders never trigger one; (b) records `chat_join_request` updates (`lib/join-requests.ts`) and `poll` updates (replaces the poll inside the stored message's `raw`); (c) marks a contact `blocked_at` on a private `my_chat_member` kick and clears it when they write again. It always sends an explicit `allowed_updates` (`POLLED_UPDATE_TYPES` in `lib/botapi.ts`) because Telegram otherwise keeps whatever list was set earlier. Anything that reacts to incoming updates therefore only works while monitoring is on.

**Background jobs** (`lib/jobs.ts`, started next to the poller from `instrumentation.ts`, 5 s tick): due **scheduled messages** (`lib/scheduled.ts` — a row is claimed `pending → sending` atomically before sending; rows found `sending` at startup are marked failed, never resent), **broadcasts** (`lib/broadcast.ts` — private chats only, deduped by `chat_id`, skips `blocked_at`, ~20 msg/s, honours 429 `retry_after`; the cursor moves *before* each send so a crash skips a contact rather than messaging anyone twice, and a cancel is noticed before every send) and a **health check** every 10 min (`lib/health.ts` → `bots.health_*`, shown on bot cards, the Info tab and the overview). Jobs use the stored token via `getBotToken` and never `withLiveBotToken`: a dead token is reported as a health error, not silently re-fetched from BotFather by a timer. Jobs look bots up with the unscoped `getBotForJob` — only for rows a scoped request handler created.

**Other bot features**: `lib/bot-clone.ts` copies profile/commands/menu button/admin rights/auto-replies to another bot of the same account (Telegram can't list which languages have overrides, so it probes `COMMON_LANGUAGES` and skips localized values equal to the default); polls are sent via `messages/poll` and stopped via `messages/[messageId]/poll`. Route conflicts for these features return 422, never 409.

**Attention panel, daily stats and digest** (`lib/attention.ts`, `lib/stats.ts`, `lib/digest.ts`; the overview's `AttentionPanel` and tile sparklines): `getAttentionItems` is read-only over the local DB and spans *all* of the dashboard user's linked accounts (revoked sessions, bots with no token, webhook errors, a monitored bot whose poller went quiet, unanswered conversations). Its inputs are columns other code must keep writing: `setPollHealth` (called by the poller after every getUpdates cycle; `recordPollHealth` in `lib/poller.ts` swallows its errors on purpose, because in the failure path a throw would skip the backoff sleep and respawn the worker in a loop) and `setWebhookHealth` (called by `GET /api/bots/[id]` and `PUT .../webhook` after they already fetched `getWebhookInfo`, so it costs no extra Bot API call). `bots.last_polled_at/poll_error/webhook_last_error/webhook_pending_count` and the `daily_stats` table back this. The poller *supervisor* (not the per-bot workers) also runs `snapshotDailyStats` (at most once per UTC day, via `__tgDashLastSnapshotDay`) and `maybeSendDigests` on every tick; the digest is guarded by `lastDigestAt` plus a per-account `singleFlight`, so a short tick overlapping a slow send can't send twice. The dashboard's `OverviewStats` carries `botsNeedingAttention` (from the health check) and `trend`.

**Capabilities and Stars**: the Info tab's Capabilities card shows the `getMe` flags (`can_join_groups`, `can_read_all_group_messages`, `supports_inline_queries`, `can_connect_to_business`, `has_main_web_app`) read-only; they're only changeable in BotFather, so each row names the command. The Revenue tab (`/api/bots/[id]/stars`) shows `getMyStarBalance` and recent `getStarTransactions` — that method pages from the *oldest* transaction, so the route walks up to 10 pages and reverses.

**Message UI customization**: inline buttons (`InlineButton`, `lib/botapi.ts`) are a label, an optional colour `style`, and exactly one action — link, `callback_data`, `copy_text`, `web_app` (https, **private chats only**) or an inline query. `validateInlineButtons`/`normalizeInlineButtons` (`lib/validation.ts`) are the single gate and the whitelist: a new button field must be added to **both**, or it is silently dropped before storage. Rows are preserved (`buttons-editor.tsx` `sameRow`). Auto-replies fire in groups too and swallow send errors, so `sendAutoReply` strips unsupported pieces per chat (`buttonsForChat`, `replyKeyboardForChat`) instead of letting Telegram reject the whole reply. A message has one `reply_markup`: inline buttons *or* a `ReplyKeyboard` (keyboard / remove / force_reply; `auto_replies.reply_keyboard`, composer, never with a file). Keyboard presses arrive as plain text, so answer them with `exact` rules; contact/location replies are rendered by `describeMessage`. Commands also support the `chat` / `chat_administrators` / `chat_member` scopes (Telegram can't list which chats have overrides), the menu button can be set for one private chat (`default` there clears it), and `message_effect_id` is sent from the composer for private chats. The effect IDs are *not* hard-coded: `lib/effects.ts` reads `messages.getAvailableEffects` over MTProto (cached 1 h) and `/api/effects` serves it; the picker hides when the list is empty.

**Inputs, callbacks and deep links** (`lib/auto-replies.ts`, `lib/templates.ts`, `lib/deep-links.ts`): auto-reply `matchType` also has `callback_prefix`, `deeplink` (`/start <payload>`, case-sensitive, checked *before* the positional list so it beats a plain `/start` rule), `media` (pattern = a kind from `MEDIA_KINDS`, which lives in `lib/validation.ts` so the client can import it) and `shared` (pattern = the `request_id` of a `request_users`/`request_chat` keyboard button). `matchAutoReply` no longer bails on messages without text: those only reach `shared`/`media` rules, private chats only. A callback rule has a `callbackAction`: `toast` (answer only), `edit` (edit the pressed message, `editMessageCaption` for media, falls back to a new message if it can't be edited, "not modified" is ignored) or `reply`; a button on an inline-mode message has no chat, so it only gets the toast. `hits`/`last_hit_at` are bumped inside `sendAutoReply`/`answerCallbackWithRule` (after the update's writes), never in the match functions, so a retry after a database error can't double-count. Reply text may use `{first_name} {last_name} {username} {user_id} {payload} {commands}`, escaped for the rule's parse mode. New reply-keyboard buttons (`request_users`, `request_chat`, `request_poll`, `web_app`, plus the old contact/location) are *at most one per button* and private-only: add any new one to `KEYBOARD_REQUEST_KEYS` (`lib/botapi.ts`, which `replyKeyboardForChat` uses to strip them in groups) and to both validate/normalize functions. Inline buttons gained `login_url` (host must be the bot's login domain) and `switch_inline_query_chosen_chat`. `bot_users.start_payload` is first-touch attribution (set only when the contact is created); `/api/bots/[id]/deep-links` stores labelled `t.me` links and counts arrivals for `start` links. Button layouts can be saved as templates (`bot_button_templates`, `ButtonsEditor` takes `botId`). A `callback_query` with `game_short_name` is answered with the URL saved in `bot_games`.

**More BotFather scripting** (`lib/botfather-apps.ts`, built on the helpers `lib/botfather.ts` now exports): `/newgame`, `/deletegame`, `/newapp`, `/myapps` delete and ownership transfer, all following the settings engine's rule (a loose hint is checked before each answer, a choice is only made when a matching button exists, anything else throws `BotFatherError` quoting BotFather → route 502). **None of these dialogues has been recorded against the real BotFather** (`BOTFATHER_APP_FLOWS_CONFIRMED = false`); the Apps & games tab and the transfer card say so. Games/Mini Apps can't be listed by Telegram, so `bot_games`/`bot_mini_apps` only mirror what was created here. Transfer confirms with the account's 2FA password via `GetBotCallbackAnswer({ password })` (SRP from `teleproto`'s `password.computeCheck`); the password is held in memory for the request only, and success is judged by `bots.getAdminedBots`, not BotFather's wording. Bot profile video (`photos.uploadProfilePhoto({ video })`), collectible usernames (`bots.toggleUsername`/`reorderUsernames`, `/api/bots/[id]/usernames`) and bulk actions on `/bots` (`/api/bots/bulk`: monitoring, health, copy settings; one bot failing never stops the rest) use MTProto/Bot API directly.

**BotFather-only settings** (`lib/botfather-settings.ts` data + `runSettingOn` in `lib/botfather.ts`, `PATCH /api/bots/[id]/botfather-settings`, Info tab → Capabilities): join-groups, privacy, inline (placeholder / off), inline feedback, inline geo, login domain. The engine never trusts BotFather's wording: a choice is sent only if a button with a matching label exists on BotFather's actual reply, a free-text answer only after the prompt passes a loose hint, and anything else throws `BotFatherError` quoting BotFather (route → 502). The conversation finishes and releases the per-user lock **before** `getMe` is read (`withLiveBotToken` can itself call BotFather to heal a token, so nesting would deadlock). The first three are re-read from `getMe` afterwards (retrying once, since it can lag): `can_read_all_group_messages` is true when privacy is **off**, so use `privacyOnFromInfo`; the rest are labelled "not confirmed by Telegram". Every `SETTING_SPECS` entry has `confirmed: false` until its real dialogue is recorded by hand and the flow matched; while any is false the Capabilities card says so (`hasUnconfirmedSettings`). The fake-client tests used so far were written to match the engine's own expectations, so they prove it fails safely, not what BotFather really says.

**Inline mode, Business chats** (all need monitoring on, since the Bot API can't list any of them):
- *Inline* (`lib/inline-results.ts`, "Links & inline" section): `inline_query` is **always** answered (an empty list when nothing matches), with a 5 s `cache_time` so dashboard edits show up quickly, and never records the asker as a contact. `chosen_inline_result` only arrives with inline feedback on in BotFather and just bumps `inline_results.uses`, scoped by bot.
- *Business* (`lib/business.ts`, `bot_business_connections`): `business_connection` updates are the only way connections are known. A `business_message` is stored with `business_connection_id`, but it is **not** a bot contact: no `bot_users`/`bot_chats` row (broadcasts walk `bot_users` and the customer never started the bot) and **no auto-reply** (it would answer as the business owner). The owner's own messages in the chat arrive as business messages too and are stored as `out` (from == the connection's user). Business chat and message IDs can repeat the bot's own chats with the same person, so everything is scoped by `business_connection_id`: edits, deletes (`deleted_at`, history is kept), the Messages grouping (conversation `key` = `chatId` or `chatId|connectionId`) and clearing a chat. Edit/pin/forward/poll routes 422 on business rows; replies send `business_connection_id` and need the connection enabled with `can_reply`.

**Bot-side chats and messaging**: the Bot API can't list a bot's chats or fetch history, so `bot_chats` (`lib/bot-chats.ts`) is filled from `my_chat_member`, group messages, and the Chats tab's "add by ID" / "import from my channels" actions; the bot's own rights there (`rights` JSON) gate which actions the UI offers. Rich sending (formatting, reply-to, URL buttons, media upload, edit/pin/forward/copy, typing) lives in `lib/botapi.ts` and `app/api/bots/[id]/messages/**`. Bot API failures go through `lib/bot-api-errors.ts`, which must never return 401 (the client treats it as a dead dashboard session) or 409 (reserved for `NO_ACTIVE_ACCOUNT`/`SESSION_REVOKED`). Media downloads (`.../media`) force non-image/video/audio types to `attachment` so user-sent HTML/SVG can't run on our origin.

**Profile photos** (`lib/photos.ts`): bot/chat/contact avatars are served by `*/photo` routes through a process-wide cache (30 min TTL, `singleFlight`, at most 3 concurrent fetches, FLOOD_WAIT-aware failure caching) and revalidated by ETag, so changed photos show up without cache-busting. Bots' and owned chats' photos are read/written over MTProto with the owner's account (no bot token needed); contact and bot-chat photos come from the Bot API (`getChat` → `getFile`). Cache keys must include the Telegram account ID.

**Usage & limits** (`lib/limits.ts`, `/api/limits`): counts from the local mirror against Telegram's limits from `help.getAppConfig` (premium-aware, cached 1 h). The bot cap is a built-in approximation because BotFather doesn't expose it.

**Request bodies**: `proxy.ts` excludes `/api/` from its matcher. Matching API routes would make Next buffer each body and truncate it at 10 MB (`proxyClientMaxBodySize`), corrupting file uploads.

**Chats** (`lib/chats.ts`, `chats` table): a local mirror of channels/groups the user owns/admins, synced from dialogs. It mainly exists to persist each channel's `accessHash`, which MTProto channel calls need and the session string doesn't keep. Use `botApiChatId()` to convert to Bot API chat IDs.

**Frontend**: `app/(dashboard)/` pages are client components that call the JSON API via `apiFetch` (`lib/api-client.ts`, throws `ApiError`). Overview (`/`) is about the active account (profile, photo via `/api/me/photo`, counts from `/api/overview`, which reads only the local DB, plus the usage-and-limits card from `/api/limits`); bots and channels/groups have their own list pages (`/bots`, `/chats`) with search + filter chips (`list-toolbar.tsx`, filter kept in `?filter=`). Pages that need an active account render `NoActiveAccount` (`no-active-account.tsx`) on `NO_ACTIVE_ACCOUNT`/`SESSION_REVOKED`. Bot/chat detail pages are split into `*-tab.tsx` components with shared types in a sibling `types.ts`. **Building a bot (Build sections, for non-technical owners)**: the bot page opens with a setup checklist on Overview (`setup-checklist.tsx`; steps are *derived* from `BotDetail` plus the rules, only "hidden"/"tried" flags live in `localStorage`) and has two Build sections. *Templates* (`lib/bot-templates.ts`, `lib/apply-template.ts`, `POST /api/bots/[id]/templates`) are plain data the client previews and the route applies; the client sends only a template ID and which parts (`profile`/`commands`/`rules`/`monitoring`), never content. Applying only **adds**: filled profile texts are kept unless `overwriteProfile`, commands merge by name, a rule whose `matchType:pattern` exists is skipped, rules go through `validateAutoReply`/`normalizeInlineButtons`, and each part reports on its own (like a clone). Template button IDs are namespaced (`tpl_<template>_<name>`) because rules match first-come in list order and new ones are appended last. The *Conversation builder* (`builder-section.tsx`, pure logic in `lib/flow.ts`) draws the existing `auto_replies` as Finder-style columns and only calls the ordinary auto-reply endpoints, so it and "All rules" (`automation-tab.tsx`) are two views of the same rows. A button can only trigger a **callback** rule, never a command rule, so "Back to the start message" works by creating a callback copy of the entry rule. "Add a button" creates the child rule *before* patching the parent, so a half-failure leaves an unused reply, never a dead button. `lib/callback-match.ts` (`findCallbackRule`) is the one matcher shared by the poller and the builder; keep it free of `db` imports, as are `lib/flow.ts`, `lib/bot-templates.ts`, `lib/format-preview.ts` and `lib/button-id.ts`, because client components import them. The rule form is one `RuleDraft` (`rule-draft.ts`) edited by `RuleFields`, used by All rules, the checklist and the builder. Auto-generated button IDs (`ButtonDraft.idAuto`) follow the label only for buttons created in the editor, never for loaded ones, or renaming a saved button would silently unlink its rule. `TelegramPreview` renders Telegram HTML/MarkdownV2 through `formatPreview` into React elements (never `dangerouslySetInnerHTML`, links carry no `href`, nothing is clickable) and fills placeholders with `fillSample` (a synchronous stand-in for `renderTemplate`).

**Build sections, round two** (templates everywhere, setup progress, previews, builder tools): the **fallback** match type ("Anything else", pattern always `*`) answers a *private* message no other rule matched, wherever it sits in the list; it never answers a bot, a group or a message that carries nothing (service messages), and a bot has at most one (`DuplicateFallbackError` in `createAutoReply`/`updateAutoReply` so clones and templates can't add a second; routes answer 422; a clone skips it). The message matcher is now the pure `lib/match-message.ts` (`matchMessageRule`, no `db` imports, like `lib/callback-match.ts`); the poller's `matchAutoReply` and the builder's test chat (`lib/simulate.ts`, `test-chat.tsx`: send/press semantics copied from the poller, runs in the browser, counts nothing, uses *saved* rules) both call it. `lib/setup-progress.ts` (pure) defines the six counted setup facts (photo, short description, description, welcome rule, commands, listening; "try it" is browser-only and not counted) used by the checklist, the sidebar badge (`page.tsx` now loads rules and photo status once and hands them to Overview) and the bot cards; the cards read `bots.setup_progress`, a JSON cache written opportunistically by whoever already knows a fact (`GET /api/bots/[id]`, the photo route, `createAutoReply`/`updateAutoReply`/`deleteAutoReply` for the `/start` rule, `setMonitorEnabled`) through `recordSetup` (`lib/setup-cache.ts`, best-effort: it swallows errors), and `cachedProgress` shows nothing until all six facts are known. Templates (18 built in, each with a `category` and `shows` tags; five use reply keyboards, deep links, `media` rules or a Mini App button, and since rules keep no state their flows advance only through buttons or unique keyboard labels) are a two-screen flow in the Templates section (gallery, then the template with *Try it* — opened on the `/start` exchange — and what it adds). People can **save a bot as a template** (`custom_templates`, per *dashboard user*, ids `custom-<n>`, `lib/custom-templates.ts`, `/api/custom-templates`; `resolveTemplate` is the one lookup for built-in and saved ones, saved ones keep switched-off rules so button targets survive), and **remove** one with `DELETE /api/bots/[id]/templates`: `planRemoval` (pure, in `lib/bot-templates.ts`, also used by the client to show counts) deletes only rules/commands that still match the template exactly (`ruleIsUnchanged` mirrors `columnsFor`) and lists the edited ones as kept. Templates can also be filtered by category in the picker and tried before applying (`simulate.ts` over the template's rules; link/copy/Mini App buttons show a note of what they'd do, and a keyboard button that requests a contact or location shares a sample one through `simulateShare`) before anything is applied; applying a second template keeps an existing `/start` rule (same `matchType:pattern` key), so use Try it to demo. Templates are offered from the empty "All rules" list (compact: only "Getting started" plus a link to all), the new-bot page (applied right after creation; a failed template never loses the bot) and bot cards without a `/start` rule, all built on `template-picker.tsx` (`TemplatePicker`, `useApplyTemplate`, `applyTemplateToBot`). `TelegramPreview` takes `fill` (default on); **broadcasts, scheduled messages, inline results and chat messages are sent verbatim, so their `ComposerPreview` passes `fill={false}`** — only auto-replies run `renderTemplate`; it also takes `media` on a message and, for the test chat only, `onSend`/`onButtonPress` (without them nothing is clickable). `ButtonsEditor` rows drag with `motion`'s `Reorder` (a `uid` per draft; the grip also takes the arrow keys; the first button is always normalised to start a row). The builder's **Map** view is `flow-map.tsx` over `flowGraph`/`pathTo` in `lib/flow.ts` (BFS from the starting points; zoom via buttons or ctrl/⌘+scroll).

**Database**: Postgres via `postgres` (postgres-js) + Drizzle, **async everywhere** (`await db.select()…`; `.returning()` gives rows, an `update`/`delete` result has `.count`). `teleproto` is a `serverExternalPackages` entry. Migrations live in `lib/db/migrations/`; the Docker image runs them at startup with `scripts/migrate.cjs` (plain JS copy of `lib/db/migrate.ts` — keep the two in sync). `docker-compose.yml` runs a `db` service (`postgres:17-alpine`, volume `tgdash-pg`); for `npm run dev` use `docker compose up db` and set `DATABASE_URL` (port 5432 is published on 127.0.0.1 only). Things that bite:
- *Atomicity is no longer free.* better-sqlite3 was synchronous, so code with no `await` could not interleave; now it can. The guards are real constraints: partial unique indexes `broadcasts_one_active_unique` (one queued/running broadcast per bot) and `auto_replies_one_fallback_unique` (one fallback rule), whose `23505` violations `isUniqueViolation` (`lib/db/errors.ts`) maps back to `BroadcastConflictError` / `DuplicateFallbackError`. Drizzle wraps driver errors in `DrizzleQueryError` — always classify through `lib/db/errors.ts`, which looks at `.cause`. Claims stay conditional `UPDATE … WHERE status='pending'` and check `.count`. Set in-memory once-per-period flags (`__tgDashLastSnapshotDay`) *before* the first `await`.
- *Raw `db.execute()` is not typed like a query.* Drizzle's postgres-js driver returns timestamps as **strings** and `count()`/`sum()` as `bigint` strings there, so convert in SQL: `extract(epoch FROM col) * 1000` as `float8`, `count(*)::int`. Typed `sql<number>` fragments need the same `::int`, and a `Date` interpolated into an `sql` template must be `toISOString()` with a `::timestamptz` cast. Use quoted aliases (`AS "botId"`) or Postgres lower-cases them. JSON text columns are read with `::jsonb`.
- Server code (`lib/`, `app/api/`, `proxy.ts`, `instrumentation.ts`) is linted with `no-floating-promises`/`no-misused-promises`/`await-thenable` (`eslint.config.mjs`; `checkThenables` is on because Drizzle queries are thenables, not native Promises, and a bare `db.delete(x);` is otherwise not flagged), so a forgotten `await` on a write fails `npm run lint` instead of silently dropping it. `next build` imports every route without `DATABASE_URL`; the pool connects lazily, so don't add an import-time throw.
