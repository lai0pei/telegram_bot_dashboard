⏺ 1. Does Telegram offer a client to manage bots?

  Only a limited one.

  Where: @BotFather (chat)
  What it does: Every management command in features.txt §22: /newbot, /token,
  /deletebot, /setinline, /setprivacy, /setdomain, games and so on.
  Limits: Text-only menus. Slow with many bots.
  ────────────────────────────────────────
  Where: BotFather Mini App (the "Open" button in the BotFather chat)
  What it does: A GUI over the same commands. features.txt line 368 lists it.
  Limits: Telegram-hosted, one bot at a time. It has no cross-bot view, no
  message history, no automation and no multi-account support.
  ────────────────────────────────────────
  Where: Managed Bots (api.txt §7)
  What it does: A "manager bot" can create bots for users and fetch, replace or
  revoke their tokens.
  Limits: Only a bot can call these, and only for bots it created. A user
  account
  can't use them, which is why lib/botfather.ts scripts the chat instead.
  ────────────────────────────────────────
  Where: Official Telegram apps
  What it does: None. They have no bot admin screen.
  Limits: n/a

  Third-party tools exist: no-code builders such as Botpress and Chatfuel, and
  helper bots such as @ControllerBot. They are mostly builders or hosted-bot
  platforms, not a self-hosted "manage all my bots, channels and accounts"
  panel. I haven't checked their current feature sets. Your dashboard sits in a
  gap Telegram itself leaves open.

  ★ Insight ─────────────────────────────────────
  - BotFather settings split into two groups. Some are Bot API calls (name,
    description, commands, menu button), and those are safe to build on. Others
    are BotFather-only (inline mode, privacy mode, join-groups, domain,
    ownership transfer, games). Those need the same chat-scripting approach as
    create/delete, so they are more fragile.
  - Because CLAUDE.md says BotFather's wording can break those flows, each
    BotFather-only feature you add makes the fragile surface bigger. Prefer
    features with a real Bot API method.
    ─────────────────────────────────────────────────

  2. What to add

  Your dashboard already covers a lot: profile, commands (localized and scoped),
  menu button, admin rights, webhook, rich messaging, polls, auto-replies,
  broadcasts, scheduled messages, health, clone, export, stats, join requests
  and chats. These are the real gaps, ranked by value for effort.

  Tier 1: high value, clean Bot API, fits the existing poller and tabs
  1. Group moderation. Ban, unban, restrict, promote, member lookup, invite
     links and forum topics. Your bot_chats already holds the bot's rights, so
     the UI can gate actions on them. This is the biggest gap from features.txt
     §6.
  2. Payments and Stars. A Stars balance and transactions view
     (getMyStarBalance, getStarTransactions), refunds, and invoice sending. It's
     read-mostly and low risk, and it covers §8 and §14.
  3. Read-only bot capability panel. getMe already reports can_join_groups,
     can_read_all_group_messages and supports_inline_queries. Showing these next
     to a "change in BotFather" deep link gives most of the benefit of the
     BotFather-only toggles with no scripting.
  4. Channel posting tools. Posting from a bot to a channel with scheduling.
     Suggested-post approve/decline is newer, so check that your Bot API version
     supports it first.

  Tier 2: useful, more work
  5. Business bot connections. Handle business_connection and business_message
  updates and show connected accounts. It extends the poller and needs new
  tables.
  6. Sticker and custom-emoji pack management. The Bot API supports it fully,
  but it's niche.
  7. Inline-mode tooling. A query log and canned inline results. It only works
  while monitoring is on.

  Tier 3: skip for now
  - Mini Apps, HTML5 games, Web Login domain and ownership transfer. These are
    BotFather-only or developer-side, with no good Bot API.
  - AI agents, guest mode and bot-to-bot. These are runtime behaviors, not
    management, and they belong in the bot's own code.
  - The Telegram API sections of api.txt (calls, secret chats, wallpapers,
    themes and so on) are client-building material and not relevant here.

  ★ Insight ─────────────────────────────────────
  - Most of Tier 1 follows existing patterns. The poller already feeds
    bot_chats, withLiveBotToken handles dead tokens, and lib/bot-api-errors.ts
    handles errors. So the cost is mostly new API routes plus a tab, not new
    infrastructure.
  - Moderation also fits your multi-tenant rule. Every action goes through
    getBotById(id, telegramAccountId), so isolation stays enforced by query
    scoping.
    ─────────────────────────────────────────────────

  My recommendation: build group moderation first, then the Stars view, then the
  read-only capability panel. Together they fill the biggest gaps without
  adding any BotFather scripting.

  Which direction fits your use? For example, are you managing mostly group
  bots, channel bots or customer-facing bots? Once you pick, I can check the
  current code in lib/botapi.ts and lib/bot-chats.ts and sketch the routes and
  tab layout.

⏺ I've planned removing Export: the card, its API route and lib/bot-export.ts,
  since the Messages tab is their only user. It needs no migration. Answers to
  your four questions:

  1. Monitoring on by default, with thousands of users?

  Thousands of people messaging one bot: yes, the poller can keep up. Each
  update is a few small SQLite writes, and getUpdates returns up to 100 updates
  per call. It's the defaults that cause trouble:
  - A webhook gets in the way. PUT /monitor refuses to enable monitoring while a
    webhook is set, because Telegram won't deliver to both. Defaulting it on
    would either fail for those bots or require deleting the webhook, which
    breaks the owner's real backend. So default it on only for bots with no 
    webhook.
  - Storage grows without limit. No retention cleanup for bot_messages turned up
    in my search. Every message, including group chatter when privacy mode is
    off, is stored forever along with its raw JSON. Thousands of active users
    means a large SQLite file. You'd want a retention setting, such as "keep 90
    days".
  - Privacy. Storing every user's messages by default is a bigger deal than
    opt-in.
  - Telegram's send limits (about 30 msg/s per bot, 1 msg/s per chat) only
    matter for auto-replies and broadcasts. The broadcast job already paces
    itself.

  Thousands of bots: this is the weaker case. The app is one Node process with
  one long-poll connection per bot. better-sqlite3 writes run on that same
  process, so heavy write load slows down page and API requests too. That works
  for hundreds of bots. For thousands, the usual approach is webhooks into a
  queue, with separate workers or a Postgres-style database.

  Verdict: fine for a few busy bots. Make it "on by default when no webhook is
  set" plus retention, and don't treat it as a design for thousands of bots.

  2. Can I sync or restore historical messages?

  For bot chats, mostly no.
  - Private chats with users: impossible. The Bot API has no history method, and
    even over MTProto a bot can't call messages.getHistory. Your linked user
    account can't read the bot's private chats either.
  - The one recovery path: Telegram keeps undelivered updates for 24 hours. If
    monitoring was off and no webhook took them, turning monitoring on fetches
    roughly the last day of updates.
  - Groups and channels: possible in principle. If your linked Telegram account
    is a member of a group or channel the bot is in, MTProto getHistory with
    that account can read its history. That would be a new "import history"
    feature, but it shows messages as your account sees them, not as the bot
    received them.

  For the Chats section (your own channels and groups), backfill over MTProto is
  fully feasible, because the account owns those chats.

  3. What is the language setting in the Commands and Settings tabs for?

  Telegram shows each user the version matching their app language
  (language_code) and falls back to the default when there's no match. That
  applies to:
  - the bot's name, description and short description (Settings tab)
  - the "/" command list (Commands tab)

  For example, a bot with German and English users can show "Hilfe" and a German
  description to German users and English to everyone else, from the same bot.
  Leave it on "Default" unless your audience speaks several languages.

  4. Menus that trigger actions: do they need a custom webhook and server?

  It depends on whether the action is static or real logic.
  - Static actions need no server. The dashboard's poller already acts as the
    backend:
    - a menu of /commands or reply-keyboard buttons, answered by Command and
      Exact rules
    - inline buttons answered by "Button answer" (callback) rules
    - links, copy-text buttons, and a Mini App menu button pointing at any
      hosted HTTPS page
  - Real logic needs code somewhere. Database lookups, calling your API or
    taking payments can't be done by fixed rules.

  If you set a webhook to your own server, monitoring stops for that bot.
  Auto-replies, the Messages history and Stats then go dark, because Telegram
  delivers to only one place.

  There's a better option that keeps both, which I'd suggest as a feature:
  forwarding from the dashboard. The poller keeps receiving updates and also
  POSTs each one, or only the ones matching a rule, to a URL you configure. Your
  server does the logic and replies through the Bot API, while the dashboard
  keeps logging and handling static menus.

  ★ Insight ─────────────────────────────────────
  - Telegram delivers each update to exactly one consumer, a webhook or
    getUpdates, never both. Most of these answers follow from that. It's why
    monitoring and webhooks exclude each other, why turning monitoring on can

  - The bot's history problem comes from bots having no access to their own
    history at all, not from any limit in this dashboard. Anything the dashboard
    didn't record while monitoring was on is gone, except the 24-hour backlog.
